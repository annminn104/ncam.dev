# AGENTS.md — apps/cd-player

## What this is

**CD Player**: any Spotify playlist or album, played on a 3D pink suitcase CD player. When a track
is about to play, its disc flies out of the crystal case held in the open lid onto the spindle,
printed with the first artist's photo; the case's booklet shows the album art, two polaroids show
the artists coming next, a "NOW SPINNING" card names the collection, and the page behind the
player is the album art blurred under the track's own colours. A self-contained Module Federation
remote (`cd_player`, :9011) that the host mounts at `/projects/cd-player`. The default collection
is the playlist `37i9dQZEVXbMDoHDwVN2tF`, "Top 50 - Global" (`DEFAULT_COLLECTION` in
`src/routes.ts`).

The stack: React 19, React Three Fiber 9 and three 0.186 (in the lazy scene chunk only), zod (in
the server code only), `@ncam/logger`, and Fraunces and Manrope through `@fontsource`. One model,
`public/assets/cd-player.glb`, generated by the Blender scripts in `art/`.

The owner's decisions (2026-10-28), which the rest of this guide assumes:

- **The official embed.** Music plays only inside Spotify's embed, driven through its iFrame API
  from the page's own controls, and the widget stays visible in the now-playing card (Spotify's
  Widget Terms). Logged-in visitors hear full tracks, everyone else 30 s previews.
- **The proxy reads embed pages.** Track lists and pictures come from Spotify's public embed pages
  (no key), because the Web API refuses its editorial playlists, Top 50 among them, to new apps.
- **Route-aware personalisation.** A pasted link becomes the page's URL (`/playlist/<id>`,
  `/album/<id>`), so it can be shared, and `localStorage` brings it back on the visitor's next
  visit.
- **The suitcase design** was approved from a Cycles render of the Blender scene (the still that
  `art/blender/scripts/hero.py` makes). There is **no finish or colour picker**.
- **No volume control**: the iFrame API has none, so the knob printed VOLUME scrubs the track.

## What it exposes

`vite.config.ts` (`defineRemote`, which sets `shared: {}` and `dts: false`) exposes three entries:

- `./mount` (`src/mount.tsx`): `mount(target, config?)`, a client render. It injects
  `styles/app.css` as `<style id="cd-player-styles">` (removed on unmount) and imports the fonts
  (`src/fonts.ts`).
- `./ssr` (`src/ssr.tsx`): `renderHeroSSR({ config?, assetBase? })` returns `{ html, css, head? }`.
  `html` is the whole shell (link bar, tracklist, now-playing card, backdrop, poster, help line,
  the "Open the player" button) for the collection the server fetched, followed by
  `<script type="application/json" id="cdp-state">` holding that data (`src/ssr-state.ts`, escaped
  so it can never end the script). `css` is `styles/fonts.css`, its `url()`s rebased onto this
  remote's origin, plus `styles/app.css`. `head` (`src/head.ts`: the collection's name and a
  description with its owner or artist and its track count) comes only on `/playlist/<id>` and
  `/album/<id>` once the collection has loaded; on `/` the host keeps its own head. `assetBase` is
  accepted for the contract and ignored.
- `./hydrate` (`src/hydrate.tsx`): `hydrate(target, config?)` reads `#cdp-state` back, hydrates
  the server markup (the host inlined the CSS) and renders the state script again, so the trees
  match.

**Route-aware** (registry `routeAware: true`). Both client entries return a `MountHandle` with
`update(route)`, which sets the route in `src/route-controller.ts`, outside React (`App` reads it
with `useSyncExternalStore`): changing collections never remounts the remote, its WebGL context
or the Spotify embed. `navigate()` only asks, through `config.onNavigate`; the host calls
`update()` back. Standalone, `src/standalone.tsx` pushes the history entry itself and follows
`popstate`. The routes (`src/routes.ts`): `/`, `/playlist/<id>` and `/album/<id>` with a
22-character base62 id; anything else renders like `/`. In the host they sit under
`/projects/cd-player`.

`config` is the host's `MountConfig`. `config.assetBase`, else the bundle's own URL
(`remoteBase()` in `src/lib/asset-url.ts`), names the GLB and the proxy, since the host page may
be on another origin.

## Data

`GET /api/spotify?type=<playlist|album|track|artist>&id=<22-character id>`
(`src/server/spotify-handler.ts`) answers with this remote's JSON (`src/spotify/types.ts`):

- `playlist` and `album`: `{ type, id, name, subtitle, tracks: [{ id, uri, title, artists, durationMs, playable, explicit }] }`;
  `subtitle` is the owner or the artist, and only `spotify:track:` entries are kept (a podcast
  episode in a playlist is dropped);
- `track`: `{ id, art: [{ url, width }], palette, artists: [{ id, name }] }`, the album art
  smallest first and the palette Spotify's own background, tinted and text colours;
- `artist`: `{ id, name, images: [{ url, width }], palette }`.

Statuses: 200; 400 `{"error":"bad_request"}` for another type or a malformed id (`no-store`); 404
`{"error":"not_found"}` for an id Spotify has no page for (`public, max-age=60, s-maxage=300`);
502 `{"error":"upstream"}` for anything else Spotify does, a status, a stall past 6 s or a page
that does not parse (`no-store`); 405 for a method other than GET, HEAD and OPTIONS, and 204 for
OPTIONS. Collections are cached `public, max-age=300, s-maxage=3600, stale-while-revalidate=86400`
(Top 50 changes daily), tracks and artists `public, max-age=3600, s-maxage=86400,
stale-while-revalidate=604800`. The handler sends its own `Access-Control-Allow-Origin: *`, and
`vercel.json` keeps its blanket header off `/api/`, so it is never doubled.

One handler runs in three places:

- **The Vercel Function** `api/spotify.ts` (a default export with `fetch(request)`). The runtime
  imports of its graph end in `.js` (`spotify-handler.ts` imports `../routes.js` and
  `../spotify/embed.js`, which imports `./schema.js`): Node ESM in the Function resolves
  specifiers as written. Keep that for any runtime import added to those files (type imports are
  erased); no test covers it, and only the deployed Function would fail.
- **Vite middleware** on the dev and preview servers (`spotifyProxy()` in `vite.config.ts`), at the
  same path. Vite's own CORS middleware (on, from `defineRemote`) runs first and answers a
  preflight itself; on every other request the handler's header replaces its Allow-Origin.
- **In-process for the server render.** `src/server/initial.ts` (`loadInitial`) calls
  `src/spotify/embed.ts` directly for the collection, its first playable track and that track's
  first artist (the backdrop and the lid's case), one after another inside a **1.5 s budget** they
  share: each fetch gets what is left as its own timeout, and one with nothing left is skipped.
  It never rejects. A miss is logged once (`cd-player.ssr-data-failed`, with the stage) and the
  client fetches that part after hydrating. A complete answer is kept for ten minutes, at most 64
  of them, the oldest out first (the host's server process outlives its requests).

**Unofficial, and where it can break.** The embed pages (`open.spotify.com/embed/<type>/<id>`)
hold their data as JSON in `__NEXT_DATA__`, at `props.pageProps.state.data.entity`. That is
undocumented, so all of it stays in `src/spotify/embed.ts` (the fetch, with a desktop Chrome
`User-Agent` because some clients get a page without data, and `readEntity`) and
`src/spotify/schema.ts` (zod, only the fields used). A change on Spotify's side becomes a 502,
never a crash: a track entry that does not fit is skipped, but a non-empty list where none fits
fails as upstream. zod and the server code stay out of the client entries' graphs
(`src/ssr-graph.test.ts`).

The browser's client (`src/spotify/client.ts`) resolves `/api/spotify` against the remote's
origin, makes one request per item at a time, keeps answers for the page's life (failures are not
kept) and is seeded with what the server render fetched. A 404 reads "We couldn't open that
playlist. It may be private or deleted.", anything else "Spotify didn't answer. Try again in a
moment." The engine fetches the details and artist of the current track and the next three
(`PREFETCH` in `src/playback/engine.ts`).

**Pictures.** Spotify's image CDN answers with `Access-Control-Allow-Origin: *`, so the scene loads
the art and the artist photos straight into textures with `crossOrigin = 'anonymous'`
(`src/scene/textures/images.ts`, an LRU of 24 images). There is no image proxy.

## Playback

**The embed loads on the first play action only** (`src/playback/embed-controller.ts`,
`IFRAME_API_SRC` = `https://open.spotify.com/embed/iframe-api/v1`), never with the page: that
click is the user activation the browser's autoplay policy wants, and it keeps the embed's
third-party cookies out of the first load, which Lighthouse's Best Practices audit counts. The
engine (`PlayerEngine.user()` in `src/playback/engine.ts`) builds the player only when a press
would start playback (the sequencer would emit a `swap` or a `load`): Repeat, Shuffle, Stop or a
seek before that loads nothing. `App`'s `createPlayer` hands it a fresh `<div>` inside the
now-playing card's `.cdp-now__embed`, where React renders nothing; Spotify swaps the div for its
iframe, 80 px high and the card's width. The script gets 15 s, building the player 20 s
(`PLAYER_TIMEOUT_MS`). If either fails (an ad blocker, a privacy setting), the card says "The
Spotify player could not load here…", the sequencer goes back to idle keeping the track, the
order, Repeat and Shuffle, and the visitor's next press tries again.

**The sequencer and its commands** (`src/playback/sequencer.ts`): a pure reducer,
`step(state, event)` returns the next state and the commands for the world outside: `swap {to}`
(change the disc in the scene), `load {uri}`, `pause`, `resume` and `seek {ms}` (the embed). The
status is `idle`, `swapping`, `playing` or `paused`. A track change emits `swap`; the engine runs it
through the bridge (`src/bridge.ts`, `swap(trackView)`) and sends **`SWAP_DONE`** once the scene
reports the disc seated, and only then does the sequencer emit **`load`**, so the music starts as
the tonearm lands. Without a live scene (the poster, no WebGL) the bridge has no swapper and the
change is instant. Only the latest change may answer (a swap token), and a change that fails still
counts as seated.

The rules: Next and Previous skip unplayable tracks (disabled in the list); Previous more than 3 s
into a track (`RESTART_MS`) restarts it; Repeat wraps the list at both ends; Shuffle is a seeded
Fisher–Yates order with the current track moved to the front; Stop pauses and goes back to the
start; a seek is held between 0 and a second before the end; a new collection keeps Repeat and
drops Shuffle. The embed ignores a seek to under a second, so `seek` in `createEmbedPlayer` takes
the start its own way: a playing track restarts (the controller's `restart()`), a paused one waits
at its first second, since a restart would play it.

Keyboard (`App.tsx`): Space plays or pauses, N and P change tracks, never with a modifier or while
focus is in a field or on a button, and a held key is one press. Every music action from the DOM
also opens the scene from the poster.

**When a track has ended** (`hasEnded`): an update paused within 500 ms of the end, or snapped back
to 0 just after being within 1.5 s of it (the same uri), never while buffering. ENDED then moves
on, or goes idle at the end of the list without Repeat. After a `load`, an event that still names
the track just left is dropped (a late "paused at its end" would end the new one); any other uri
passes, because Spotify may report a relinked track under another id.

**The hint.** Right after `loadUri` the embed reports itself paused until the audio starts, so the
engine ignores paused updates until `playback_started`. If that has not come 3.5 s after a load
(`HINT_MS`), the card says "Press play inside the Spotify card to start." (an iframe the browser
would not let play by itself), and the note goes once playback starts. A slow machine can take
longer than that over the first track (7 to 11 s from the press in headless Chromium on
SwiftShader), so the hint may show for a moment and go by itself.

**No volume.** The iFrame API has no volume, so the knob scrubs (see "The scene"). Per Spotify's
Widget Terms the widget stays visible in the card while it plays: never hide it, and never play
the audio any other way.

## The scene

**A lazy chunk.** `src/shell/SceneHost.tsx` imports `src/scene/PlayerScene.tsx` behind
`import.meta.env.SSR`, so the server build drops it, and only once the boot starts. Nothing `App`
imports reaches three, `@react-three/*` or `src/scene/` statically; `src/ssr-graph.test.ts` walks
the three entries' graphs and pins it. The files the scene shares with the shell (`src/bridge.ts`,
`actions.ts`, `scene-props.ts`, `playback/sequencer.ts`, `lib/asset-url.ts`, `fonts.ts`) stay
three-free for that reason, and so do `boot.ts`, `failure.ts`, `webgl.ts` and `autoplay.ts`, which
ask about WebGL without three.

**The phases** (`src/boot.ts`, a pure reducer, garden-home's shape): `poster` → `booting` →
`live`, or `error` over the poster. Events: `start` ("Open the player", and "Try again" for a
failure that can be retried in place), `autostart`, `ready` (three frames of the player drawn,
`useReadyProbe` in `PlayerRig.tsx`) and `fail`. `autostart` only ever leaves the poster: it comes
when the page has settled on a hardware GPU and with every music action from the DOM, so a failed
boot is retried by "Try again" alone. While booting the scene layer is invisible and `inert`; on
`ready` it fades in over 600 ms (`FADE_MS` in `src/App.tsx` equals the `.cdp-scene` transition in
`styles/app.css`; keep them equal), then the poster unmounts.

**Autostart on a hardware GPU** (`src/autoplay.ts`, the same logic as mini-store's and
garden-home's copies; keep the three in step): once the page has loaded and the main thread is
idle (`whenSettled`), the scene starts by itself when WebGL2 runs on a hardware GPU (a context made
with `failIfMajorPerformanceCaveat`, and a renderer that is not SwiftShader, llvmpipe, softpipe or
Microsoft Basic Render) and the visitor has not asked for reduced motion. On a software rasteriser
(the Lighthouse runner) the poster waits for the visitor.

**Failures** (`src/failure.ts`, shown by `src/shell/EnterButton.tsx` in a `role="alert"` over the
poster; the music plays on): no WebGL2 (`hasWebGL2()` in `src/webgl.ts`, asked before any canvas
mounts): "This browser can't draw the 3D player. The music still plays.", with no button; a chunk
that would not load (`SceneChunkError`): "The 3D player couldn't start. The music still plays."
with **Reload the page** (a browser remembers a failed dynamic import, and the reload stops the
music, hence the label); anything else (the GLB, the model contract, a render-time throw caught by
`SceneBoundary`): the same message with **Try again**. Each is logged as `cd-player.scene-failed`.

**The GLB contract** (`src/scene/contract.ts`): `REQUIRED_NODES` are the pivots `lid_hinge`,
`arm_pivot`, `knob` and `btn_prev`, `btn_next`, `btn_play`, `btn_stop`, `btn_rpt`, `btn_mode`, the
templates `disc` and `case` (with `case_lid_hinge`), `polaroid_a`, `polaroid_b`, `card`, and the
empties `disc_seat` (on the spindle) and `case_seat`; `DYNAMIC_MATERIALS` are the six materials the
page paints (`art_disc`, `art_booklet`, `art_photo_a`, `art_photo_b`, `card_print`, `lcd_screen`).
`loadPlayerModel` (`src/scene/model.ts`, GLTFLoader with the meshopt decoder) throws
`ModelContractError` naming what is missing. `src/scene/model-contract.test.ts` reads the committed
GLB: every required node, every printed material and a role for every material, UVs on every
printed and tiled primitive, the budget, and meshes on leaf nodes only.

**Material roles** (`src/scene/material-roles.ts`, three-free so the contract test can read it;
`materials.ts` builds them). The GLB carries the base colour, roughness and metalness tuned in
Blender; the role adds what glTF cannot say: leather (sheen, a light clearcoat and a pebble-grain
normal map made at runtime, `textures/grain.ts`), fabric, lining, plastic, matte, crystal
(transmission 1, IOR 1.53, a faint specular so the booklet reads through it), metal, brushed
(anisotropy), disc-data and foil (iridescence), gloss-black, emissive, print and screen. A name
without a role falls back to plastic, but the contract test fails first. The studio is in
`PlayerScene.tsx`: a PMREM'd `RoomEnvironment` (`scene.environmentIntensity` sets every material's
reflections), a key light that casts (2048 px shadow map, 1024 on a narrow screen), a rim and a
hemisphere light, AgX tone mapping, a device pixel ratio of at most 2 (1.5 on a narrow screen), a
transparent canvas and a shadow-only floor, so the page's backdrop shows round the player.

**The rig** (`src/scene/rig.ts`, `rigFor`, one per model): **two discs and two cases**, so one pair
can leave while the next arrives, each with its own copies of `art_disc` and `art_booklet` so they
print differently. Disc `i` belongs to case `i`; `lidCase` is the case shown in the lid, `seated`
the disc on the spindle (null before the first play), and `swapping` a change in progress (the
texture hook leaves the lid alone meanwhile). The discs live at the root and fly in world space.

**The director's timelines** (`src/scene/director.ts`, pure functions of the time, tested):
`insert`, the first play (1.1 s: the lid's case opens, its disc flies down onto the spindle, the
case closes, the arm swings in and lowers), and `change` (2.8 s: the arm lifts and swings to its
rest; the disc rises and flies back into the lid's case, which opens and closes on it; that case
lifts out of the tray, flies aside and shrinks away while the next track's case grows in from the
other side, opens, and its disc flies down; the arm swings in and lowers). `restingPose` holds
between changes: the arm on the disc while a track is loaded, 200 rpm while it plays.
`src/scene/swap-controller.ts` is the bridge's swapper, with no React and an injected clock so node
tests drive it, and every change it runs settles: a new change first ends the one in progress, a
change waits at most 1.5 s for its prints (`PRINT_WAIT_MS`), a change asked for in a hidden page
finishes at once, a running one also ends on the clock (its duration + 250 ms) when no frame comes,
and a teardown settles the one in progress at once. `seat(view)` puts the lid's disc on the spindle
when a track plays with no change for it (the scene booted mid-playback, or Play reloaded the
current track after its player failed). `src/scene/useDirector.ts` draws the poses in R3F's frame
loop.

**Printed textures** (`src/scene/textures/`): canvases, painted in the page's own faces
(`loadFaces` loads them first, because canvas text never asks the page for a font): each disc's
label (1024 px square: the artist's photo, else the album art, with the title and artists round
the rim in capitals), its case's booklet (1024 px square, the album art), the two polaroids (512 px,
the next two tracks' artists), the card (1024 × 182, "NOW SPINNING" and the collection) and the LCD
(256 × 112, the track and the time, repainted at most once a second). Before any art they show the
page's own defaults. `canvasTexture` keeps **`flipY = false`**: `export.py` lays each print's UVs
over its mesh's local bounds in Blender and the glTF exporter flips V, so the canvas's top row is
the print's top, as GLTFLoader's own maps assume; with three's default `flipY` a print would come
out flipped top to bottom. The last print started on a disc wins (`painter.ts`; the director aborts
the older one), a print that fails or stalls never stops a change, a print made in the fallback
faces is made again once the fonts are in, and `reprintFor` prints a track again when its art
arrives after its change began.

**Controls and the orbit** (`src/scene/controls.ts`, `useControls.ts`, `interaction.ts`,
`orbit.ts`, `CameraRig.tsx`):

- **The deck keys** press on the **primary button** (or a touch), and only the nearest mesh under
  the pointer counts. On pointerdown `btn_prev`, `btn_next`, `btn_play` (play or pause), `btn_stop`,
  `btn_rpt` (Repeat) and `btn_mode` (Shuffle) emit their `PlayerAction` through the bridge
  (`BUTTON_ACTIONS`), and the key sinks 1.2 mm and comes back over 160 ms (`PRESS_MS`). The cursor
  turns to a hand over a key or the knob.
- **The knob scrubs the track.** A turn is followed on the window, read around the middle of the
  knob's top (its pivot sits at its base), and one full turn is 30 s (`KNOB_MS_PER_TURN`). It emits
  one `seek {deltaMs}` only on a real release; a cancelled turn, or a mouse that moves with no
  button down (a native menu took the release), puts the knob back where the turn began and seeks
  nothing.
- **A drag elsewhere orbits the view** (the primary button or a touch), within ±25° of yaw and ±10°
  of pitch, eased (`orbit.ts`). It **recentres on a mouse double-click, or a touch double tap**
  (two taps within 350 ms and 30 px, neither moving more than 10 px), unless that lands on a
  control. `interaction.controlActive` tells the camera that the latest pointerdown went to a key
  or the knob (R3F's handler runs after the camera's), so that press neither orbits nor recentres;
  a mouse release that was lost (`releaseLost`) disarms both drags.
- **`leaveOnDeck`** re-parents, at runtime, what the model hangs from the moving pivots although it
  is printed on the deck: each key's dark ring and label (`player_btn_gap_*`, `player_btn_lbl_*`),
  the dial's ticks (`player_tick_*`) and its VOLUME label (`player_vol`), so only the key or the
  knob moves. A model rebuild whose Blender scripts already parent those to the deck can drop it
  (and its tests in `controls.test.ts`).
- `.cdp-canvas` sets `touch-action: none` and `user-select: none`.

**The one framing rule** (`src/scene/framing.ts`): `frameForViewport(width, height, yaw, pitch)`
and `isWide(width)` (wide above 820 px, where the tracklist becomes a drawer beside the player).
`CameraRig` holds that frame every frame (resizes included), `PlayerScene` sizes the shadow map and
the pixel ratio by `isWide`, and the poster capture goes through the same code. A wide screen aims
right of the player so it sits clear of the drawer; between 821 and 1260 px the link bar stacks and
the framing keeps its height free; a narrow screen stands further back and aims lower, clear of the
now-playing card. `framing.test.ts` projects the model's box through it at every screen shape the
layout has. Known misses: on a single-row screen shorter than about 760 px the bar can cover the
lid's top rim.

**Reduced motion** (`prefers-reduced-motion: reduce`): no autostart; a disc change is instant (the
rig jumps to its end and the music still waits a 300 ms beat, `REDUCED_MOTION_MS`); the backdrop's
cross-fade, the tracklist's equaliser, the canvas's fade-in and the phone sheet's slide are off
(`styles/app.css`). The disc still spins while a track plays, and the orbit still eases.

## Personalisation

The URL names the collection: `/playlist/<id>` or `/album/<id>` (`src/routes.ts`), that is
`/projects/cd-player/playlist/<id>` in the host, so a page can be shared; **Share** in the link bar
copies `location.href`. Loading a pasted link (`loadLink` in `src/App.tsx`):

1. `parseSpotifyLink` (`src/spotify/link.ts`) takes an `open.spotify.com` or `play.spotify.com` link
   with or without `https://`, `intl-xx/`, `embed/` or a query string, a `spotify:` URI, or a bare
   22-character id (taken as a playlist). A track, artist, episode, show or user link is refused as
   not a playlist or an album; `spotify.link` short links are not followed.
2. The collection is fetched; only once that succeeds is `{ type, id }` saved in `localStorage`
   under **`ncam.cd-player.last`** (`src/persist.ts`) and the page navigated there. The engine
   then loads the new collection into the same mount.

**Restore on `/`**: an App that mounts on `/` navigates to the saved collection (`restoreTarget`),
never to the default playlist, and it looks only when it mounts, so Back to `/` (a route update,
not a remount) stays there. A fresh mount (the host opening the project again) restores again.
Opening someone else's shared link does not replace the visitor's saved one, since only a pasted
link is saved. Storage that is blocked or full just forgets (`safeStorage`).

## Art pipeline (`art/`)

```
art/blender/scripts/  cdkit.py (geometry helpers, Principled materials, millimetres), parts.py (the
                      CD, the crystal case, the polaroid, the player), build_player.py (the web
                      scene, with the names the page drives), export.py (the background entry),
                      hero.py (the Cycles still)
art/blender/tools/    bl.py: a client for a running Blender's add-on socket (design sessions only)
art/pipeline/         build.mjs: Blender headless, then gltf-transform
art/.out/             scratch: the raw export and the renders (gitignored)
```

`art/README.md` lists the scripts. `art:build` (`art/pipeline/build.mjs`) needs **Blender 5.2.2
LTS** (`/Applications/Blender.app`, or `BLENDER_BIN`) and runs it with `--background
--factory-startup --python-exit-code 1` (Blender exits 0 when a script raises) on `export.py`,
which execs `cdkit.py`, `parts.py` and `build_player.py`, sets **`WEB = True`** (cdkit's web
quality: about half the segments, bevels at a resolution of 2 at most, none of the Cycles-only
shader tricks), turns curves and text into meshes, gives the tiled materials (leather, lining,
fabric, deck, grille) box-mapped UVs at one unit per 5 cm and the printed ones planar UVs over their
bounds, and writes `art/.out/cd-player.raw.glb`. gltf-transform then dedups accessors, meshes and
textures (never materials: the five prints start identical and would merge into one), welds, prunes
(keeping the empty pivots, and the UVs that no texture in the file uses yet) and meshopt-compresses
it into `public/assets/cd-player.glb`, which is **committed** (about 576 KB and 73,539 triangles
today). **The budget** (`model-contract.test.ts`): 4 MB, 150k triangles, `EXT_meshopt_compression`,
and meshes only on leaf nodes, so quantisation never scales a pivot. Rebuild after any change to the
scripts, then capture the poster again. The deck's lettering uses macOS fonts (Avenir Next, DIN
Alternate and Futura, loaded by `use_scene` in `cdkit.py`); elsewhere Blender's own font stands in
and the GLB changes.

`hero.py` renders the Cycles product still the design was approved from, into `art/.out/` (the art
it prints comes from `CDP_HERO_ART`). It is for docs; the build never runs it, and the approved
still is not in the repository.

**The socket tool.** `art/blender/tools/bl.py` drives a running Blender through the Blender Lab MCP
add-on's socket at `127.0.0.1:9876`: it sends `{"type": "execute", "code": …, "strict_json": false}`
followed by a NUL byte and reads JSON up to the next NUL; the code assigns a JSON-serialisable dict
to `result` to return data (`python3 -I bl.py <file.py>`, or `-c "<code>"`). It is for design
sessions in a live Blender only: nothing in the build needs it. In a live Blender a render goes
through the window's scene under `temp_override` (`render()` in `cdkit.py`), and the first Cycles
render on Metal spends about two minutes compiling its kernels.

## Poster

`src/assets/poster/` holds AVIF at three widths per shape (landscape 1280, 1920 and 2560; portrait
480, 750 and 1080) plus one WebP per shape (landscape 1920, portrait 750), with alpha. They are
imported from JS (`index.ts`), so `defineRemote`'s `renderBuiltUrl` names them from this remote's
origin, on the server too; `poster.test.ts` pins the declared sizes, the capture and the alpha.
`src/shell/Poster.tsx` shows the portrait one at or below a square viewport, the landscape one
above, with `object-fit: cover`; its `<img>` is the page's one `fetchpriority="high"` image. The
poster is the scene as it boots, **captured with alpha and the default prints** (a track's change
daily): the page's own backdrop shows round the player, and the canvas fades in over it.

`capture:poster` (`scripts/capture-poster.mjs`) needs the dev server (`CD_PLAYER_PORT` set for both,
or `CD_PLAYER_URL`) and Playwright's Chromium. It loads `/?capture=landscape|portrait`
(`src/capture.ts`; `src/scene/CaptureScene.tsx` draws the scene alone with its default prints, the
page's fonts loaded first and the page's own background cleared) at **1280 × 720, scale 2** and
**390 × 844, scale 1080/390** on SwiftShader, waits for `window.__sceneReady`, takes a screenshot
without a background and writes the eight files with sharp. Any page error fails the run.
`CAPTURE` in `src/capture.ts`, `SHAPES` in the script and the sizes in `index.ts` move together.

The poster matches the live framing exactly only at those two aspects: the framing follows
`isWide`, the poster the aspect ratio, so other shapes jump a little at the fade, and a portrait
tablet wider than 820 px gets the phone capture while its framing is the wide one. **Capture again
after any change to the model, the lights, the camera or the framing, or the default prints.**

## Deploying

The Vercel project **`ncam-cd-player`** (Root Directory `apps/cd-player`, the Vite preset,
`SITE_URL` set to the host's public origin) also deploys `api/spotify.ts` as the Function at
`/api/spotify`. `vercel.json` sends `Access-Control-Allow-Origin: *` on every path except `/api/`
(the handler sends its own), revalidates `/assets/cd-player.glb` (`public, max-age=0,
must-revalidate`: its name never changes), rewrites `/playlist/<id>` and `/album/<id>` to
`index.html` for the standalone page, and keeps Dependabot's branches from deploying. Docker: the
compose service `cd-player` shares the host container's network (`network_mode: service:portfolio`,
9011 published on `portfolio`), the `Dockerfile` takes `CD_PLAYER_REMOTE_URL` as an `ARG`, and
nginx has the `cd_player` upstream and a `cd-player.localhost` server block.

**Owner tasks before the merge goes live** (`docs/deployment.md` → "Adding a remote to the live
site"), in this order:

1. Create the Vercel project `ncam-cd-player` (Root Directory `apps/cd-player`, `SITE_URL` set)
   and deploy it.
2. Check that the Function answers:
   `https://ncam-cd-player.vercel.app/api/spotify?type=playlist&id=37i9dQZEVXbMDoHDwVN2tF` should
   return the playlist as JSON (the Function's build cannot be tried locally).
3. On the host project, set
   `CD_PLAYER_REMOTE_URL=https://ncam-cd-player.vercel.app/remoteEntry.js` (**with**
   `/remoteEntry.js`) and redeploy the host.
4. Merge. Merged first, the host bakes in `localhost:9011` and the gallery lists a page that cannot
   load.

## Known facts and gotchas

- **Spotify answers an unknown id with HTTP 200**: a page whose `pageProps` is `{ status: 404, … }`
  with no `state`, so `readEntity` checks for the entity itself (no entity on the 404 page is a 404;
  no entity on any other page is a 502).
- **The embed reports itself paused right after `loadUri`**, until the audio starts. The engine
  ignores paused updates until `playback_started` (`awaitingStart`), or every new track would read
  as paused at once.
- **Logged out, and in Safari** (which blocks the embed's third-party cookies by default), the embed
  plays Spotify's **30 s previews**; full tracks need a Spotify login in the same browser. Headless
  Chromium gets the previews too.
- **Cycles blocks shadow rays at glass**, so in a Cycles render whatever sits inside the crystal
  case comes out dark; `mat()` in `cdkit.py` lets shadow rays through a Transparent BSDF, only when
  `WEB` is false. It is a design-render concern only: the web scene's glass casts no shadow at all
  (`upgradeMaterials` in `src/scene/materials.ts`).
- On `/projects/cd-player/playlist/<id>` the host titles the page with the remote's `head`
  (`<name> · CD Player · ncam.dev`) and its description; on `/projects/cd-player` it uses the
  registry's name and tagline. The visitors' pages are not in the sitemap (`routeAware: true`, no
  `sitemapPaths`).
- **The embed ignores a seek to under a second** (`seek(0)` included), and a paused embed reports a
  seek only once it plays again; Previous and Stop rewind through `restart()` and a seek to 1 s
  (see "Playback").
- Stop, Repeat, Shuffle and the scrub exist only on the 3D deck; the now-playing card has Previous,
  Play and Next, and the keyboard Space, N and P. On a 390 px phone a deck key is about 9 px
  across and the knob 18, and from the hero view the knob hides much of the MODE key (Shuffle).
- Console noise that is not this app's: `THREE.Clock: This module has been deprecated` comes from
  R3F 9.8.2 itself, and `Allow attribute will take precedence over 'allowfullscreen'` from
  Spotify's iframe.
- Rebuilding after a build that overrode `CD_PLAYER_REMOTE_URL` (the Lighthouse build with
  `LH_PORT_OFFSET`, a host smoke against :9111) needs `pnpm build --force`: a Turbo cache hit
  writes the cached outputs back but leaves the overridden build's extra chunks in
  `apps/portfolio/.output`.
- `curl` and `wget` are blocked in the agents' environment: probe `/api/spotify` with a small
  `.mjs` that calls `fetch`, run with `node`.
